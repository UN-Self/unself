# Unself 产品蓝图

> 来源：docs/PRODUCT_SPEC.md v3（2026-09-10，PM 视角全量设计）§0/§1/§2/§12；现状与约束来自 docs/requirements.md §0。
> 一句话定位：**跑在 Cloudflare 上、模块自选组合、按量计费的自托管团队工作台**
>
> Unself 不是 SaaS，不提供中心化租户或统一托管服务。每个团队在自己的 Cloudflare 账户、服务器或私有基础设施中部署一套独立实例，并自行选择身份、邮件、日历、存储、聊天和会议模块。

## 产品定位（2026-09-10 拍板）

**Unself 真正交付的是三样东西：**

1. **壳**——登录、成员、审批、通知、审计、工作台，把模块装进同一个入口；
2. **契约**——manifest + module-sdk + Core API + 模块注册表启停，这套「约束和范式」让模块可插拔、可替换、可自研；
3. **装配器**——把「你选了什么」物化成 Cloudflare 资源的部署引擎（幂等收敛）。

**模块是载荷，不是产品。** 聊天、日历、文档、邮件等官方模块是「改编工艺」的示范和参考实现：fork 成熟项目后按契约大刀阔斧改造，或包一层外部服务做成适配器。第三方团队照着同一套契约，可以写适配层、部署自己的 Cloudflare 服务，拼出他们自己想要的团队管理软件。

**生态位对比：**

| 产品 | 形态 | 问题 |
|---|---|---|
| 飞书等综合 SaaS | 不许单点的自助餐 | 为用不上的 AI/企业功能买单，小团队养不起 |
| 纯聊天/单点工具 | 只有一道菜 | 功能太窄，支撑不了团队其他协作 |
| **Unself** | **在 CF 按量计费的地基上自选组合** | 不要的能力永远不部署、不存在、不花钱；想要而没有的，契约在手自己写 |

**能力轴模型（本版核心形态原则）：** 身份、邮件、聊天、日历、存储……每项能力是一根独立的轴，用户的选择向量 = 该实例的产品形态；壳 + 契约是常量，模块全是变量——这就是 pay-as-you-go 的结构本质，计费模式只是它的财务投影。空壳（内置身份 + 零模块）本身合法：一个轻量团队目录，往上每加一个模块长一个能力。

## 产品是什么（做完之后的样子）

一个团队部署完成后，只需要一个入口：

```text
https://team.example.com
```

统一壳根据管理员启用的模块动态生成左侧导航：

```text
┌─────────────────────────────────────────────────────┐
│  https://team.example.com  （自托管工作台）             │
│                                                       │
│   工作台   消息   日历   看板   文档   会议   管理       │
│                                                       │
│   以上菜单只显示已启用的模块。EdgeChat 未启用时不显示消息。│
│   [左侧] 模块导航   [中间] 当前模块   [右侧] 详情/通知    │
└─────────────────────────────────────────────────────┘
```

每次部署对应一个独立团队，不存在 Unself 中央 SaaS 租户、租户切换或多团队管理。模块可以来自 Cloudflare Worker、Docker 服务或外部系统，但对用户呈现为同一个工作台。

**团队成员的日常是**：

- 打开团队自己的工作台，看到已启用模块的未读通知、今日日程和待办事项；
- 如果启用了 EdgeChat，点击“消息”进入单聊、群聊、文件和逐条已读回执；未启用时，系统不显示也不部署聊天模块；
- 从消息、任务或日历创建会议，会议模块使用 Cloudflare Worker/DO 提供信令，音视频优先在浏览器之间 P2P 传输；
- 使用可选的文档、看板、日历和 Git 动态模块；
- 邮件、身份、日历和文件存储可以使用团队已有服务，不要求必须使用 Stalwart 或 Cloudflare R2。

**管理员的日常是**：配置身份、启用模块、绑定外部服务、管理本团队成员和权限、查看审计和备份状态。邮箱开户、停用等动作只有在配置了对应的 Provisioning 适配器时才自动执行。

## 角色与权限

| 角色 | 谁 | 权限 |
|---|---|---|
| 管理员 | 该实例所属团队的管理员 | 管理本团队成员、模块、外部服务、审计和业务设置 |
| 用户 | 正式成员 | 使用已启用且被授权的模块 |
| 访客 | 外部协作者 | 只读或受邀参与指定模块，无默认团队权限 |

**身份原则**（2026-09-10 范式修订）：Unself 不要求“邮箱账号 = 唯一身份”。**登录能力核心内建**——内置账号（用户名+密码）为默认形态，外部 OIDC 为可选增强，两者并存时按 email 合并为同一用户。身份不是模块：模块装载（iframe + module-token 换发）以已登录会话为前提，依赖方向决定了身份必然在壳/核心层。内置用户以 username 识别；OIDC 用户以 `instance_id + issuer + sub` 识别，`email` 作为联系方式或显示字段。

忘记密码：内置账号没有邮件兑底时，由管理员在成员页手动重置——这是无邮件实例的唯一恢复路径。

## 需求 → 模块 → 复用/自研 对照表

模块按来源与形态分三类（2026-09-10 拍板）：

| 类 | 是什么 | 例子 |
|---|---|---|
| 功能模块 | 原生 Worker 实现的协作能力，随实例部署 | EdgeChat 改编、会议信令、看板 |
| 适配器 | 代码随实例部署，包一层外部系统接入工作台 | Stalwart（邮件）、CalDAV（日历）、Webhook（Git） |
| 伴生服务 | 实例外的整台服务，只做配置接线 | Stalwart 本体、外部 IdP、TURN/SFU |

三类开发方式、部署方式、信任边界各不相同，下表的「默认实现」一列不再混为一谈。

| # | 能力 | 默认实现 | 可替换实现 | 组合规则 |
|---|---|---|---|---|
| 1 | 登录与身份 | 核心内建：内置账号默认 + OIDC 客户端可选 | Keycloak、Authentik、Stalwart 等外部 OIDC | 必选核心能力，**非模块**；身份轴与邮件轴正交 |
| 2 | 工作台 | 自研 Shell | Vue/React 前端部署 | 必选基础模块 |
| 3 | 即时通讯 | EdgeChat Cloudflare Worker + DO | 其他聊天系统适配器 | 可选，未启用时不显示“消息” |
| 4 | 日历 | CalDAV/iCalendar | Stalwart、Nextcloud、其他 CalDAV 服务 | 可选 |
| 5 | 看板/任务 | 自研轻量模块 | 外部任务系统适配器 | 可选 |
| 6 | Markdown 文档 | 自研模块 + 编辑器库 | 外部文档系统适配器 | 可选 |
| 7 | P2P 会议与会议记录 | Cloudflare Worker + DO 信令；浏览器本地录音/转写 | MiroTalk 或其他 WebRTC 信令服务；外部 ASR/AI | 可选；媒体默认不经过 Worker，文档输出和 AI 纪要均可选 |
| 8 | 文件存储 | S3 兼容适配层 | R2、MinIO、用户自备 S3 | 可选 |
| 9 | 邮件 | SMTP 适配器 | Stalwart、其他 SMTP 服务 | 可选，仅启用通知或邮箱能力时需要 |
| 10 | 资源开通 | 无 | Stalwart API、SCIM、Webhook | 可选，OIDC 本身不负责创建邮箱 |
| 11 | Git 动态 | Webhook 适配器 | Gitea、GitHub、GitLab | 可选 |
| 12 | AI/MCP | 平台协议和适配器 | 各模块自行提供工具 | 可选 |

## 与飞书的差异（明说，避免期待错位）

| 飞书有 | 我们 | 备注 |
|---|---|---|
| 云文档（富文本协同） | md 文档 | 够用但非富文本 |
| 多维表格（Bitable） | 看板 + 日历联动 | 轻量替代 |
| 视频会议（SFU，百人） | P2P（建议 ≤6 人） | 小团队场景 |
| 审批流/考勤等 HR 模块 | 无 | 自建按需 |
| 移动端原生 App | PWA + Android 壳 | 体验接近但不推送后台通知（安卓壳除外） |

### 产品与参考部署的边界

- **产品能力**：任何团队可在自己的 Cloudflare 账户、Docker 环境或两者组合中部署独立实例；身份、邮件、日历、聊天、会议、存储都可按模块启停或替换。
- **官方部署**：Cloudflare 交互式装配器 CLI（一键入口为路线图），自动创建或绑定所需的 Workers、D1、KV、R2 和 Durable Objects 资源。
- **Docker 角色**：替代部署方式，以及 TURN、SFU、录制和不适合 Workers 的可选组件运行环境。
- **本团队参考部署**：Stalwart、Gitea、openresty、Tailscale 和 unself.cn，作为官方示例与首个生产实例。

### 硬约束与默认原则

1. **自托管而非 SaaS**：每个部署者运行自己的独立实例，数据和组织配置不离开其账户/基础设施。
2. **Cloudflare 优先**：正式路径=交互式装配器 CLI（决策 #2，一键为路线图）；核心功能必须可由 Workers/Pages 等 Cloudflare 产品运行。
3. **可组合部署**：Docker 和外部服务用于扩展、替代部署或不适合 Workers 的能力，不能破坏核心模块的独立启停。
4. **开放身份**：内置账号（用户名+密码）为默认登录；外部 OIDC 为可选增强（决策 #4/#20），不要求使用特定邮局或邮箱域名。
5. **低运维**：默认模板让非专业运维也能完成部署和升级；复杂网络组件按需启用。
6. **大陆可用**：参考部署需要满足中国大陆团队的访问体验。
