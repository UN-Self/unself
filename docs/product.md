# Unself 产品蓝图

> 来源：docs/PRODUCT_SPEC.md v3（2026-09-10，PM 视角全量设计）§0/§1/§2/§12；现状与约束来自 docs/requirements.md §0。
> 一句话定位：**跑在 Cloudflare 上、模块自选组合、按量计费的自托管团队工作台**
>
> Unself 不做 SaaS，也没有中心化租户或统一托管这一说。每个团队都在自己的 Cloudflare 账户、服务器或者私有基础设施里部署一套独立实例，身份、邮件、日历、存储、聊天、会议这些模块自己挑。

## 产品定位

**Unself 真正要交付的，就三样东西：**

1. **壳**——登录、成员、审批、通知、审计、工作台，把各个模块收进同一个入口；
2. **契约**——manifest + `@unself/sdk` + Core API，再加模块注册表的启停。这一套「约束加范式」定下来，模块才能插拔、能替换、能自己写；
3. **安装器**——只把 core 和 workbench 部署到 Cloudflare。模块不在这一步装。

**模块是载荷，不是产品。** 聊天、日历、文档、邮件这些官方模块，是「改编工艺」的示范，也是参考实现：fork 一个成熟项目，按契约大刀阔斧地改；或者包一层外部服务，做成适配器。第三方团队照着同一套契约写适配层、部署自己的 Cloudflare 服务，就能拼出他们想要的团队管理软件。

**生态位对比：**

| 产品 | 形态 | 问题 |
|---|---|---|
| 飞书等综合 SaaS | 不许单点的自助餐 | 为用不上的 AI/企业功能买单，小团队养不起 |
| 纯聊天/单点工具 | 只有一道菜 | 功能太窄，支撑不了团队其他协作 |
| **Unself** | **在 CF 按量计费的地基上自选组合** | 不要的能力永远不部署、不存在、不花钱；想要而没有的，契约在手自己写 |

**能力轴模型（本版核心形态原则）：** 身份、邮件、聊天、日历、存储……每项能力都是一根独立的轴，用户选出来的这个向量，就是这个实例的产品形态。壳和契约是常量，模块全是变量——这也是 pay-as-you-go 的结构本质，计费模式只是它在财务上的投影。空壳（内置身份 + 零模块）本身也合法：它就是一个轻量团队目录，往上每加一个模块，就多长出一项能力。

## 产品是什么（做完之后的样子）

一个团队部署完之后，只需要一个入口：

```text
https://team.example.com
```

统一壳会根据管理员启用的模块，动态生成左侧导航：

```text
┌─────────────────────────────────────────────────────┐
│  https://team.example.com  （自托管工作台）             │
│                                                       │
│   工作台   消息   日历   看板   文档   会议   管理       │
│                                                       │
│   以上菜单只显示已启用的模块。聊天模块没装上时不显示消息。│
│   [左侧] 模块导航   [中间] 当前模块   [右侧] 详情/通知    │
└─────────────────────────────────────────────────────┘
```

一次部署就是一个独立团队。没有 Unself 中央 SaaS 租户，也没有租户切换、多团队管理这回事。模块可以来自 Cloudflare Worker、Docker 服务或者外部系统，但用户看到的始终是同一个工作台。

**团队成员平时是这样的**：

- 打开团队自己的工作台，看已启用模块的未读通知、今天的日程和待办；
- 装了聊天模块，点「消息」就能进频道、文件和逐条已读回执；没装，侧栏不显示消息；
- 从消息、任务或者日历起一个会议。会议模块用 Cloudflare Worker/DO 做信令，音视频优先在浏览器之间走 P2P；
- 用可选的文档、看板、日历和 Git 动态模块；
- 邮件、身份、日历和文件存储都能用团队已经有的服务，不非得用 Stalwart 或者 Cloudflare R2。

**管理员平时干的活**：配身份、开模块、绑外部服务、管本团队成员和权限，再看审计和备份状态。邮箱开户、停用这类动作，只有配了对应的 Provisioning 适配器才会自动跑。

## 部署

平台两条路：安装器只把 core 和 workbench 部署到 Cloudflare；或者写好 env，用 Docker 拉起 workbench。模块不在这一步装。

模块不由安装器部署（具体步骤见 [docs/deploy.md](deploy.md)），启动时先连上 core，用哪类资源由安装时选定。

成员只在侧栏里看到已经装上的模块。

## 角色与权限

| 角色 | 谁 | 权限 |
|---|---|---|
| 管理员 | 该实例所属团队的管理员 | 管理本团队成员、模块、外部服务、审计和业务设置 |
| 用户 | 正式成员 | 使用已启用且被授权的模块 |
| 访客 | 外部协作者 | 只读或受邀参与指定模块，无默认团队权限 |

**身份原则**（2026-09-10 范式修订）：Unself 不要求「邮箱账号 = 唯一身份」。**登录能力是核心内建的**：内置账号（用户名+密码）是默认形态，外部 OIDC 是可选增强，两个都在的时候按 email 合并成同一个用户。身份不是模块：模块装载（iframe + module-token 换发）得先有已登录会话，依赖方向摆在那儿，身份只能在壳和核心层。内置用户用 username 认；OIDC 用户用 `instance_id + issuer + sub` 认，`email` 只当联系方式或者显示字段。

忘记密码：内置账号又没有邮件兜底的时候，管理员到成员页手动重置——这是无邮件实例唯一能走的路。

## 需求 → 模块 → 复用/自研 对照表

模块按形态分三类，包都是 npm 包：

| 类 | 是什么 | 例子 |
|---|---|---|
| 功能模块 | 原生 Worker 实现的协作能力，随实例部署 | 聊天、会议信令、看板 |
| 适配器 | 代码随实例部署，包一层外部系统接入工作台 | Stalwart（邮件）、CalDAV（日历）、Webhook（Git） |
| 伴生服务 | 实例外的整台服务，只做配置接线 | Stalwart 本体、外部 IdP、TURN/SFU |

这三类的开发方式、部署方式、信任边界都不一样，所以下面这张表里「默认实现」一列不能混着说。

| # | 能力 | 默认实现 | 可替换实现 | 组合规则 |
|---|---|---|---|---|
| 1 | 登录与身份 | 核心内建：内置账号默认 + OIDC 客户端可选 | Keycloak、Authentik、Stalwart 等外部 OIDC | 必选核心能力，**非模块**；身份轴与邮件轴正交 |
| 2 | 工作台 | 自研 Shell | Vue/React 前端部署 | 必选基础模块 |
| 3 | 即时通讯 | 聊天模块 `@unself/chat`（已在仓库里） | 其他聊天实现 | 可选，没装时不显示“消息” |
| 4 | 日历 | CalDAV/iCalendar | Stalwart、Nextcloud、其他 CalDAV 服务 | 可选 |
| 5 | 看板/任务 | 自研轻量模块 | 外部任务系统适配器 | 可选 |
| 6 | Markdown 文档 | 自研模块 + 编辑器库 | 外部文档系统适配器 | 可选 |
| 7 | P2P 会议与会议记录 | Cloudflare Worker + DO 信令；浏览器本地录音/转写 | MiroTalk 或其他 WebRTC 信令服务；外部 ASR/AI | 可选；媒体默认不经过 Worker，文档输出和 AI 纪要均可选 |
| 8 | 文件存储 | core 的 S3，或模块自己的存储 | 不另做适配层 | 可选 |
| 9 | 邮件 | SMTP 适配器 | Stalwart、其他 SMTP 服务 | 可选，仅启用通知或邮箱能力时需要 |
| 10 | 资源开通 | 无 | Stalwart API、SCIM、Webhook | 可选，OIDC 本身不负责创建邮箱 |
| 11 | Git 动态 | Webhook 适配器 | Gitea、GitHub、GitLab | 可选 |
| 12 | AI/MCP | 平台协议和适配器 | 各模块自行提供工具 | 可选 |

## 与飞书的差异（明说，避免期待错位）

| 飞书有 | 我们 | 备注 |
|---|---|---|
| 云文档（富文本协同） | md 文档 | 够用但非富文本 |
| 多维表格（Bitable） | 看板 + 日历联动 | 轻量替代 |
| 视频会议（SFU，百人） | P2P（建议 ≤6 人） | 小团队场景 |
| 审批流/考勤等 HR 模块 | 无 | 自建按需 |
| 移动端原生 App | PWA + Android 壳 | 体验接近但不推送后台通知（安卓壳除外） |

### 产品与参考部署的边界

- **产品能力**：任何团队都能在自己的 Cloudflare 账户、Docker 环境，或者两者混着来，部署一套独立实例；身份、邮件、日历、聊天、会议、存储都能按模块启停或者替换。
- **官方部署**：Cloudflare 交互式装配器 CLI（一键入口在路线图上），自动创建或者绑定需要的 Workers、D1、KV、R2 和 Durable Objects 资源。
- **Docker 角色**：它既是一种替代部署方式，也是 TURN、SFU、录制这些不适合 Workers 的可选组件的运行环境。
- **本团队参考部署**：Stalwart、Gitea、openresty、Tailscale 和 unself.cn，既是官方示例，也是第一个生产实例。

### 硬约束与默认原则

1. **自托管而非 SaaS**：每个部署者跑自己的独立实例，数据和组织配置都不离开他的账户和基础设施。
2. **Cloudflare 优先**：正式路径是交互式装配器 CLI；核心功能必须能由 Workers/Pages 这类 Cloudflare 产品跑起来。
3. **可组合部署**：Docker 和外部服务用来扩展、替代部署，或者承接不适合 Workers 的能力，但不能破坏核心模块的独立启停。
4. **开放身份**：内置账号（用户名+密码）是默认登录方式，外部 OIDC 是可选增强，不要求用哪个邮局或者哪个邮箱域名。
5. **低运维**：默认模板让不懂运维的人也能完成部署和升级；复杂网络组件按需启用。
6. **大陆可用**：参考部署要满足中国大陆团队的访问体验。
