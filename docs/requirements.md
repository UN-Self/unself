4. **运维简单**：Docker 化（/root/docker/<service> 惯例），管理员为个人而非专业运维
5. **自助化优先**：成员自助完成注册/密码管理，管理员只做审批

## 7. 第一性原理技术评估（初版）

### 架构原则
1. **实时通道必须自建常驻进程**：已读未读等状态推送需要长连接（WebSocket），Serverless 的冷启动与按请求计费不适合做实时核心 → **IM 核心放自有 VPS**
2. **Serverless 用于"非实时"边角**：注册门户、审批通知、Webhook、定时任务等事件驱动型逻辑
3. **日历不重复造轮子**：Stalwart 自带 CalDAV/JMAP 日历（含会议邀请 accept/decline），只写前端或接现成客户端
4. **存储外置可配置**：附件/大文件写入用户自备 S3 兼容存储（R2/MinIO），通过可配置的后端适配
5. **视频走 P2P**：信令服务器只负责协调，媒体流不经过自家服务器，流量成本为零

### 技术选型与复用调研（v2：二次开发缝合路线）

> 用户决策：不是部署现成产品，而是**二次开发把模块缝成一套精简产品**。

| 模块 | 基底（fork/复用） | 二次开发要做的事 |
|---|---|---|
| 统一壳 | 自研 Vue3/React 单页壳（飞书式左侧导航） | 身份、导航、跨模块跳转、通知中心 |
| IM | **EdgeChat**（aozorae/Edgechat，CF Workers+Hono+DO+D1+KV+R2，GPL-3.0，中文） | 接 Stalwart 邮箱身份；加**逐条已读回执**（现有 message_reads 表只有频道级游标）；改 UI 融入统一壳 |
| 日历 | **Stalwart CalDAV**（后端零开发） | 前端日历界面（FullCalendar 类库）+ 会议邀请 UI |
| 看板/任务 | 轻量库或自研（不部署 Vikunja） | 看板视图 + CalDAV VTODO 同步到日历 |
| md 文档 | 轻量编辑器库（如 Milkdown/Tiptap） | 协作保存 + 权限 |
| 视频会议 | **MiroTalk P2P**（仅信令，媒体 P2P） | 嵌入统一壳，会议链接与日历事件联动 |
| 文件 | S3 兼容适配层（R2/MinIO 可配置） | IM 附件/文档/头像统一走适配层 |
| 门户/审批 | Serverless 函数或边缘 Worker | 注册申请→审批→调 Stalwart API 开号 |

### EdgeChat 能力盘点（已读源码）
- ✅ 账号体系：管理员建号 + **邀请注册**（RegisterPage + InviteManager，邀请码即审批凭证）
- ✅ 实时：Durable Objects WebSocket Hibernation（免费额度友好）
- ✅ 群聊/私聊/语音消息/文件/头像/历史分页/@提醒/封禁
- ✅ 文件存 R2（S3 兼容，天然符合"用户自备桶可配置"诉求）
- ✅ 管理后台：仪表盘/用户管理/邀请/站点设置
- ⚠️ **已读未读：只有频道级已读游标（未读计数+@优先），无逐条"已读 x/y"回执 → 需二次开发**
- ⚠️ 认证：自建用户名密码（D1 存储），无 OIDC → 需接 Stalwart 邮箱身份
- ⚠️ 平台绑定：Durable Objects 是 CF 专属 → 选 EdgeChat 即选 CF；换其他 serverless 商则实时层需重写

### 部署拓扑（初版）
```
unself.cn 子域入口（openresty 反代）
 ├─ mail.unself.cn      → Stalwart（邮件+日历+身份）
 ├─ chat.unself.cn      → EdgeChat（CF 边缘，fork 后自部署）
 ├─ meet.unself.cn      → MiroTalk（P2P 信令，媒体不落服务器）
 ├─ signup/portal       → 边缘 Worker（申请/审批，接 Stalwart API）
 └─ 附件               → 用户自备 S3 兼容桶（R2/MinIO 可配置）
```

### 与原有 P0 的衔接
- 注册/审批门户 = 统一身份入口（P0 第一步）
- Gitea 集成保持不变（审批制 + @unself.cn + 内部通知）
- 三层权限：管理员=handy 等，用户=正式成员，访客=外部协作人员（只读/受限）
